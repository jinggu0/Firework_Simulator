# V2 시간축 반짝임 지표

## 왜 새 지표가 필요했나

- V2-3a의 초해상 기준 지표는 **LOD 페이드를 악화로 판정**한다(V2-3b). 기준 쪽이 더
  상세하므로, 1×에서 표현 못 할 디테일을 올바르게 기댓값으로 수렴시킬수록 차이가 커진다
- 게다가 그 지표가 잰 "눈에 띄게 틀린" 픽셀의 과반은 **AO 추정기 잡음**이었다(V2-3c)
- V2-1a의 이동 델타는 정상적인 화면 이동까지 포함하므로, 그 보고서 스스로 반짝임
  점수가 아니라고 밝혔다

## 방법

- **카메라 중심을 축으로 한 요 회전.** 순수 회전이면 화면 이동이 카메라 행렬만으로
  정확히 정해지고 **깊이와 무관**하다. 따라서 이전 프레임을 그 이동대로 옮기면 다음
  프레임이 예측된다
- **예측 잔차 = 장면과 함께 움직이지 않은 것.** 격자보다 가는 디테일이 엉뚱한 속도로
  기어가는 것, 모서리가 미끄러지지 않고 계단처럼 튀는 것, 표면이 지나가는데 화면에
  고정된 채 남는 잡음 패턴이 모두 여기 잡힌다
- 그래서 **LOD 페이드를 올바르게 판정**한다. 기댓값으로 수렴한 화면은 깨끗이 움직이므로
  점수가 좋아진다(합성 테스트로 고정)
- 시뮬레이션 시간 동결(dt=0), 평면 반사는 매 프레임 재렌더(시간이 멈추면 원래 일정으로는
  첫 자세의 반사가 경로 내내 남아 지연이 반짝임으로 오인된다)
- 24프레임(23쌍, 최소 20쌍), 화면 중심 속도 **0.618 px/프레임**(황금비 켤레 — 경로 위
  어떤 두 프레임도 중심에서 정수 픽셀만큼 떨어지지 않아, 격자에 다시 맞물려 숨는
  에일리어싱이 없다). 기울어진 카메라는 요 한 단계가 화면을 덜 쓸므로 행렬로 보정한다
- 보간은 3차 B-스플라인. 프리필터가 프레임 경계 너머로 |z|^n(z=√3−2)만큼 번지므로
  7px 테두리를 점수에서 뺀다(경계 영향 1e-4 미만)
- 점수는 픽셀별 **잔차 RMS**다
  - 선형 HDR 휘도: 픽셀 평균 대비 **5%** 초과를 불안정으로 센다(`measure_aliasing`과 동일)
  - 표시 프레임 휘도: **2 코드값** 초과(`frame_comparison.temporal_stability`와 동일)
- 알려진 드라이버 잔차 영역은 경로 이동량만큼 넓혀 제외한다

```powershell
python -m tools.measure_temporal_shimmer --ambient-occlusion-off --static-control
```

## 지표 자체의 검증

지표가 재야 할 것을 실제로 재는지부터 확인했다.

### 합성 정답 테스트 (`tests/test_temporal_shimmer.py`, 15개)

측정값(테스트는 괄호 안의 조건을 단언한다):

| 경우 | 불안정 비율 | 평균 잔차 |
|---|---:|---:|
| 격자가 표현 가능한 줄무늬(0.08 주기/px)가 강체 이동 (안정) | 0% | 2.5e-05 |
| 격자보다 가는 줄무늬(0.8 주기/px) 점표본 (불안정) | 100% | 0.296 |
| 같은 줄무늬를 64배 초해상 박스 표본 (잔차 절반 미만) | 100% | 0.069 |
| 같은 디테일을 기댓값으로 페이드 (**초해상보다 좋음**) | 0% | 1e-16 |
| 화면에 고정된 잡음 × 움직이는 장면 (불안정) | 71.0% | 0.053 |
| **같은 잡음**을 표면에 부착 (안정) | 0% | 3.6e-04 |
| 정지 카메라·동일 프레임 (0) | 0% | 1e-16 |

초해상 박스 표본은 잔차를 23%로 줄이지만 **여전히 전 픽셀이 불안정**하다. 1픽셀 박스
필터는 0.8 주기/px 성분을 약하게 할 뿐(sinc 0.23) 없애지 못한다. 기댓값 페이드만 0이 된다.
화면 고정 잡음과 표면 부착 잡음은 **같은 잡음 필드**이고 차이는 무엇에 붙어 있느냐뿐이다.

이 밖에 테두리 제외, 최소 쌍 수 거부, 절대 임계(코드값), 제외 마스크, 최악 블록 위치,
그리고 카메라 수학 3건(같은 카메라는 항등, 오른쪽으로 돌면 내용이 왼쪽으로, **위로
기울이면 내용이 이미지 행 아래로** — V0-8의 행 순서 함정을 테스트로 고정)이 있다.

### 뮤턴트 확인

일부러 틀린 구현을 넣어 테스트가 잡는지 봤다: 이동 보정 없음, 이동 방향 반대, 이미지
행 뒤집힘 — **세 가지 모두 잡힌다**.

### 실제 렌더에서 이동 예측 검증 (`motion_prediction_check.json`)

예측이 옳다면 예측 좌표에 어떤 일정한 부분 픽셀 오프셋을 더해도 잔차가 줄어서는 안 된다.
0.1px 간격 ±0.4px를 프레임 전체와 3×3 타일마다 탐색했다(AO 끔 — AO 잡음은 화면에
고정돼 최소점을 "이동 없음" 쪽으로 끌어당긴다).

- 격자가 디테일을 분해하는 `facade_landmark`: 전체 최소 **(0, 0)**, 타일 **8/9**가 (0, 0)
- 세로 방향 최소는 세 시점 모두 0이다
- `water_reflection`과 `road_ground`는 1×에서 가로 +0.3, +0.2px에 최소가 있었다. 이것이
  예측 오류인지 확인하려고 **같은 회전을 4× 초해상으로 렌더해 박스 평균**했더니
  `water_reflection`의 최소가 **[0.0, 0.0]**로 돌아왔고, 원경 스카이라인이 있는 가운데
  타일 줄이 +0.2/+0.4/+0.2 → **0/0/0**이 됐다. 1×의 치우침은 예측 오류가 아니라
  **격자보다 가는 디테일(에일리어싱)**이다 — 이 치우침 자체가 에일리어싱의 서명이다
- 구조가 거의 없는 하늘 타일 줄은 4×에서도 약간 음수로 남는다(잔차가 너무 작아 위치를 못 잡음)

### 보이는 프레임에서 AO는 정지 지표가 말한 것보다 작은 몫이다

| 시점 | 정지 초해상 지표의 AO 몫 | 이동 HDR의 AO 몫 | 이동 **표시**의 AO 몫 |
|---|---:|---:|---:|
| terrain_shoreline | 73% | 43% | 21% |
| grass_close | 87% | 63% | 30% |
| road_ground | 90% | 52% | 5% |
| facade_landmark | 72% | 41% | 21% |
| bridge_structure | 53% | 13% | 0% |
| water_reflection | 54% | 5% | 0% |

- V2-3c의 정지 초해상 지표는 여섯 시점 모두에서 오류의 과반을 AO로 돌렸다. 카메라가
  움직일 때 **보이는 프레임**에서는 AO 몫이 0~30%로 모든 시점에서 소수다. 정지 지표를
  그대로 믿었다면 AO부터 고쳤을 것이다
- 선형 HDR에서는 근경 시점에서 AO 몫이 크다(최대 63%). 상대 임계는 어두운 픽셀에
  민감하므로(V2-3c의 `water_reflection` 교훈) 보이는 크기는 표시 프레임으로 읽어야 한다

### 보이는 반짝임은 원경의 밝은 창에 몰려 있다

AO를 끈 뒤 표시 프레임 기준 최악은 `bridge_structure`(22.77%)와
`facade_landmark`(14.20%)다. 최악 블록 위치:

- `bridge_structure`: 상위 5개 블록이 행 320~368·열 256~336 — 원경 스카이라인의 불빛 띠,
  최악 블록 평균 잔차 RMS **약 45 코드값**
- `facade_landmark`: 행 80~320·열 272~352 — 멀리 있는 붉은 골조 타워의 작은 창
- `terrain_shoreline`: 행 304~384·열 496~800 — 강 건너 스카이라인과 그 수면 반사

위치는 V0-8에서 확인한 "원거리 창 셀이 2픽셀 미만" 조건과 맞는다. 다만 이 시점들에서
셀 크기를 직접 재지는 않았으므로 **위치에 근거한 추정**이다. V2-3b가 검사하려 했으나
잘못된 시점 때문에 판정하지 못한 가설이며, 이제 이 지표로 판정할 수 있다.

### `road_ground`에서 보정 후 점수가 더 높았던 이유

보정 없음(1.84%)이 보정(3.33%)보다 낮았다. 원인을 추적했다:

- 화면 위쪽 회색 영역은 하늘이 아니라 **0.8~1.8m 앞의 표면**이다(깊이로 확인). 거기 박힌
  2~3픽셀 크기의 어두운 점은 **AO를 끄면 전부 사라진다**(75 → 0픽셀). scene이나 haze를
  꺼도 남고(79, 78), land를 끄면 화면이 바뀌어 오히려 늘었다(395)
- AO 회전 난수는 셰이더 코드상 화면 좌표에 묶여 있어 카메라가 돌아도 **제자리에 남는다**.
  프레임 차분은 이를 못 보고 이동 보정을 해야 드러난다 — 지표가 설계대로 동작한 경우다
- 이 시점이 **렌즈 1m 앞의 표면을 주로 보고 있다**는 것은 V2-3c에서 남은 위험으로 적은
  주제 가시성 문제를 더 구체적으로 확인한 것이다

## 부수 발견: 렌더러의 카메라 방향이 float32로 반올림된다 (`camera_direction_rounding.json`)

일정한 요 간격인데 쌍마다 중심 이동이 달랐다(`facade_landmark` 0.561~0.629px). 원인은
렌더러다. `Renderer._update_camera`는 `_look_at(position, position + forward)`로 뷰를 만들고,
`_look_at`은 방향을 float32의 `target - eye`로 되찾는다. 원점에서 수백 m 떨어진 위치에서는
이 뺄셈이 위치의 float32 간격으로 방향을 반올림해 **카메라가 고르지 않은 걸음으로 돈다**.

- 방향 오차 최대: grass_close 1.0e-05 rad(0.009px) ~
  road_ground 3.9e-05 rad(**0.033px**)
- 같은 카메라를 원점에 두면 3e-08 rad 이하 — 위치 크기 탓임을 확인
- 반짝임 측정에는 영향이 없다. 도구가 같은 float32 행렬을 만들므로 예측 이동에 반올림이
  포함되고, 보고서의 쌍별 중심 이동 범위가 곧 그 들쭉날쭉함이다
- 고치지 않았다. 방향에서 직접 뷰를 만들면 원점 밖 모든 카메라의 렌더 출력이 바뀌므로,
  측정 도구 추가가 아니라 전후 캡처가 필요한 별도의 렌더 변경이다

## 한계

- 카메라 중심 회전에는 시차가 없어, 이동(평행이동)할 때만 생기는 불안정(반사, 가려짐
  해제)은 재지 않는다
- **흐리게 만드는 변경도 안정적으로 점수가 나온다.** 수정안을 판정할 때는 무엇을
  지웠는지(블록 평균 밝기, 해상 가능한 대역의 디테일)를 함께 봐야 한다 — 이 하한 장치는
  아직 없다
- 표시 점수에는 인간 시각 변환이 섞여 있다. 주변시 흐림이 화면 좌표에 묶인 밉 레벨을
  표본화하므로, 표시 불안정 중 관찰자 모델의 몫은 분리되지 않았다
